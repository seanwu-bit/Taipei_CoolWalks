# 🌳 靜態綠意與基礎路網建構 (Static Greenery & Base Network)

本專案節點負責處理「臺北市大安區」的人行基礎路網萃取，以及靜態樹木資料（綠意遮蔭）的空間聚合與拓樸重建。我們旨在將原始的地理空間資料，轉化為後續「路徑導航演算法」與「微氣候分析」可無縫接軌的權重路網圖台。

---

## 📌 1. 本階段核心工作 (What We Did)

本部分聚焦於**以「行人」為本**的路網環境建構與靜態綠意評估：
1. **人行路網萃取與精煉**：捨棄高快速道路與汽車主幹道，篩選出符合行人與自行車真實移動情境的生活巷弄、步道與次要道路。
2. **綠意空間交集 (Spatial Join)**：匯入大安區實體樹木點位資料（`Trees_Daan.shp`），將每棵樹精準映射至對應的街道緩衝區內。
3. **路段權重計算**：量化每條路段的「樹木數量 (Tree Count)」、「有效遮蔽當量 (Shading Equivalent)」與「行人安全分數 (Safety Score)」。
4. **圖論拓樸還原**：將細分計算後的權重，重新聚合 (Aggregate) 回原始的 OSM 路網架構中，確保演算法能正確讀取節點關係。

---

## 🚀 2. 整個 IPYNB 在做什麼？ (Workflow Overview)

整個 `Static Greenery& Base Network.ipynb` 依序執行了以下四大任務：

* **[Task 0] 環境設定與目標鎖定**：環境套件掛載，連接 Google Drive，並以「臺北市大安區」為分析目標 (AOI)。
* **[Task 1] 人行環境基礎路網萃取與細分 (Densification)**
  * **過濾主幹道**：利用 Custom Filter 精準剔除高架/快速道路。
  * **路寬屬性補全 (Imputation)**：自動推算缺失的路寬屬性。
  * **幾何細分**：將過長道路以 `50m` 為最大閾值進行切分，確保綠意統計能反映極局部的微氣候。
  * **動態緩衝區**：依照 `(路寬/2) + 3m` 建立動態偵測範圍。
* **[Task 2] 實體樹木空間交集與遮蔽量統計**
  * 執行向量點與多邊形的 `sjoin` (Spatial Join)，統計各分段路網範圍內的實體樹木量與遮蔭指數。
* **[Task 3] 拓樸還原與資料匯出**
  * 將 50m 細分路網的分數（平均值/加總值）還原聚合至原始 OSM 拓樸架構。
  * 清理屬性並匯出多種格式 (CSV, GeoJSON, GPKG)。
* **[Task 4] 數據交接模擬與完整性檢視 (Handoff Simulation)**
  * 腳本內建防呆測試，模擬後續同學讀取資料，驗證屬性分布與拓樸正確性。

## 📦 3. 產出與交付檔案 (Deliverables for Next Team)

為了讓後續負責「路徑演算法 (Pathfinding)」與「前端視覺化」的同學能無縫接軌，我們提供了**雙軌制**的資料包：

### A. 細分版 (供高解析度熱區分析 / 地圖渲染使用)
* 檔案前綴：`Daan_Shaded_Network(分段)_v1`
* **`.geojson`**：包含細分後的路段幾何與屬性，供前端快速渲染地圖。
* **`.csv`**：純文字屬性權重檔。
* **`.gpkg` (GeoPackage)**：同時封裝 `edges` (路段) 與 `nodes` (節點) 圖層，GIS 軟體標準格式。

### B. 還原版 (⭐ 演算法組核心輸入 - 推薦使用)
* 檔案前綴：`Daan_Shaded_Network(還原)_v1`
* **`.csv`**：保留原始路網屬性，並已**明確包含 `u`, `v`, `key` 欄位**，可供 NetworkX 直接建立圖形 (Graph) 進行 Dijkstra / A* 路徑運算。
* **`.geojson`** & **`.gpkg`**：還原後的幾何圖形與節點圖層，供演算法組於視覺化檢查時疊圖使用。

## 🛠️ 4. 遭遇困難與 AI 診斷 / 防呆機制 (Troubleshooting & Proactive Safeguards)

在資料處理過程中，我們遭遇了 GIS 與 Graph 數據轉換的經典陷阱，並透過 AI 輔助提前加入了防呆機制：

### 🛑 困難 1：OSM 拓樸斷裂 (遺失 `u`, `v`, `key` 節點索引)
* **問題描述**：在 Pandas 的 `merge` (屬性合併) 或匯出為非圖論格式 (如 GPKG) 的過程中，OSMnx 隱藏在 MultiIndex 中的起訖點資訊 (`u`, `v`, `key`) 會被系統自動丟棄，導致後續演算法組無法重建路網圖。
* **AI 防呆修正 (Index Recovery)**：在所有匯出與合併步驟前，強制寫入 `reset_index()`，將隱藏的圖論結構釋放為實體欄位 (`columns`)。並在輸出 CSV 時，嚴格指定必須匯出 `['u', 'v', 'key', 'osmid', ...]`，徹底免除交接後的斷圖危機。

### 🛑 困難 2：地理資料屬性型別衝突 (Export Crashes)
* **問題描述**：OSMnx 抓下來的部分欄位 (如 `highway`, `name`) 有時會是 List 或 Dict 格式（例如一條路有多個名稱）。這會導致 `to_file()` 轉換為 GeoJSON 或 GPKG 時直接崩潰報錯。
* **AI 防呆修正 (Attribute Cleaning)**：實作 `clean_attributes(gdf)` 函數，巡邏所有欄位，自動將任何非基礎型別的物件強制轉為字串 (`astype(str)`)，確保資料輸出的高相容性。

### 🛑 困難 3：大範圍路寬與遮蔽高估
* **問題描述**：一開始若給定過大的固定 Buffer，會把馬路對面或公園深處的樹木也算進「行人遮蔭」中，造成數值失真。
* **優化修正**：不依賴全區固定半徑，而是補全路寬資料後，設計 `半徑 = (路寬 / 2) + 3m` 的動態幾何緩衝，確保只涵蓋實際對該路段有影響的行道樹。
